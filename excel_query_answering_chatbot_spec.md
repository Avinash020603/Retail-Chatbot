# Excel Query-Answering Chatbot — Project Specification

## 1. Project Overview

Build a conversational chatbot that answers natural-language questions about data stored in Excel workbooks (`.xlsx` / `.xls`) and CSV files. The chatbot should support both:

- **Structured queries:** numeric calculations, filters, grouping, sorting, joins across sheets/tables, date ranges, and aggregations.
- **Unstructured or text-heavy queries:** searching descriptions, comments, notes, feedback, and other free-form text by meaning or keywords.
- **Hybrid queries:** combining database calculations with evidence retrieved from text fields.

The project should be modular, safe, testable, and easy to extend. Start with a local prototype and keep the architecture ready for PostgreSQL and production deployment.

## 2. Goals and Non-Goals

### Goals
1. Let users ask questions in plain English.
2. Convert structured questions into validated SQL and execute them against imported data.
3. Retrieve relevant text records for semantic or keyword questions.
4. Combine SQL and text retrieval when a question needs both.
5. Return concise answers with supporting rows, sources, and a clear explanation of calculations.
6. Ask a clarification question when a request is ambiguous or required fields are unclear.
7. Handle missing values, invalid questions, and query errors gracefully.
8. Keep database operations read-only by default.

### Non-Goals for the first version
- Editing source Excel workbooks.
- Executing arbitrary Python or shell code generated by an LLM.
- Supporting every Excel formula or complex workbook feature.
- Automatically making business decisions from the data.
- Requiring cloud services for a local proof of concept.

## 3. Recommended Initial Stack

- **Language:** Python 3.11+
- **Data loading and cleaning:** pandas, openpyxl
- **Prototype database:** SQLite (`sqlite3` or SQLAlchemy)
- **Future/production database:** PostgreSQL (`psycopg` or SQLAlchemy)
- **Text retrieval:** start with keyword search; optionally add embeddings and a vector index later
- **LLM orchestration:** use a provider-neutral interface; LangChain or LangGraph may be added if useful
- **Interface:** CLI first, then Streamlit or FastAPI if needed
- **Testing:** pytest
- **Configuration:** environment variables and a `.env` file (never commit secrets)

Do not use both SQLite and PostgreSQL in the initial prototype unless there is a concrete requirement. Use a database adapter/repository layer so the backend can be changed later.

## 5. Data Ingestion and Workbook Handling

Implement an ingestion pipeline that:

1. Accepts one or more `.xlsx`, `.xls`, and `.csv` files.
2. Lists workbook sheets and lets the user select which sheets to import.
3. Reads each sheet into a pandas DataFrame.
4. Normalizes column names for database use while retaining original names in metadata.
5. Infers and validates data types (integer, decimal, date/time, boolean, text).
6. Handles blank rows, duplicate column names, missing values, and malformed data.
7. Imports each sheet into a separate table by default.
8. Stores metadata mapping the original workbook, sheet, original column name, normalized column name, and inferred type.
9. Reports import warnings and row counts.
10. Does not silently discard rows or overwrite existing tables without confirmation.

Important considerations:
- Excel may contain multiple header rows, merged cells, formulas, formatted values, and inconsistent types. The first version can require a single header row and clearly report unsupported formats.
- Excel formulas are not a substitute for a calculation engine; pandas/openpyxl may not recalculate formulas.
- Define a policy for table names and duplicate sheet names.
- Avoid loading extremely large workbooks fully into memory without a size check.

## 6. Query Classification and Routing

Create a query planner that classifies each user question into one of these routes:

### A. Structured SQL
Use when the question requires exact filters, counts, sums, averages, rankings, group-bys, date comparisons, or joins.

Examples:
- “What was the total revenue in September?”
- “Show the top 10 products by sales.”
- “Which department has the most open requests?”
- “Compare monthly totals for the last two years.”

### B. Text Search / Retrieval
Use when the question asks about the meaning or content of descriptions, comments, notes, or feedback.

Examples:
- “Find comments that mention battery problems.”
- “What reasons do customers give for low ratings?”
- “Find complaints similar to ‘excessive noise at night.’”

### C. Hybrid
Use when a question needs both database calculations and text evidence.

Examples:
- “Which product category has the most negative reviews, and what are the main complaints?”
- “Which department has the most unresolved cases, and what issues are mentioned most often?”
- “Compare average ratings for products whose reviews mention battery life.”

### D. Clarification / Unsupported
Ask a targeted question if the requested metric, date range, table, or meaning is ambiguous. Explain when the workbook does not contain the necessary data. Do not invent missing facts.

The classifier should return a small structured plan, such as:
- route: `sql`, `text`, `hybrid`, or `clarify`
- relevant tables and columns
- required operations
- retrieval terms or semantic intent
- assumptions and missing information

Validate the plan before execution.

## 7. Structured Query Generation and SQL Safety

For structured questions:

1. Give the LLM only the relevant schema and a few safe examples, not the entire database contents.
2. Ask it to generate a SQL `SELECT` query and a brief description of the intended operation.
3. Parse and validate the query before execution.
4. Allow only read-only operations in the first version. Reject statements such as `INSERT`, `UPDATE`, `DELETE`, `DROP`, `ALTER`, `CREATE`, `ATTACH`, and multiple statements.
5. Use parameterized values for user-provided literals wherever possible.
6. Add a query timeout or other execution limits where supported.
7. Limit returned rows and result size; paginate or summarize large outputs.
8. Handle database errors without exposing secrets or internal stack traces to the end user.
9. Verify that referenced tables and columns exist.
10. Do not rely on an LLM prompt alone for SQL safety—enforce safety in code.

SQLite is convenient for a local prototype. PostgreSQL is preferable when multiple users, central access control, larger workloads, or operational management are needed. The application should use a configurable database adapter.

## 8. Text Retrieval

Start with a simple, measurable baseline:

### Baseline: keyword search
- Index relevant text columns.
- Use SQLite FTS5 when available, PostgreSQL full-text search, or a simple fallback.
- Return matching rows with row IDs and source workbook/sheet information.

### Optional upgrade: semantic search
- Create embeddings for text columns such as `description`, `comments`, `review_body`, or `notes`.
- Store embeddings in a vector index appropriate to the chosen backend.
- Retrieve top-k relevant records using semantic similarity.
- Optionally combine keyword and semantic results using reciprocal rank fusion (RRF).
- Keep metadata filters so users can restrict search by date, category, status, or source sheet.

Do not assume every text column should be embedded. Select columns based on profiling and user needs. Rebuild or update the index when source data changes.

## 9. Hybrid Query Execution

For hybrid questions, do not ask the LLM to answer from a vague summary alone. Create a plan with explicit steps.

Example question: “Which product category has the most negative reviews, and what are customers complaining about?”

Possible execution:
1. Query the database for counts/ratings grouped by category.
2. Define “negative” explicitly (for example, rating <= 2) or ask the user if the threshold is unclear.
3. Retrieve representative review text for the leading categories.
4. Identify recurring complaint themes from retrieved evidence.
5. Produce a response containing the numerical comparison and representative text evidence.
6. Cite the relevant row IDs, workbook/sheet, and columns.

Where possible, use SQL for exact counts and averages, not LLM arithmetic.

## 10. Answer Format and Evidence

Answers should:
- Directly answer the question first.
- Show calculations, filters, and date ranges when material.
- Include a small table for grouped or ranked results.
- Identify the source workbook and sheet, and relevant row IDs when available.
- Distinguish computed facts from qualitative summaries.
- State uncertainty, missing values, or assumptions.
- Avoid fabricating records, statistics, quotations, or citations.
- Say when the data does not support an answer.

For text-based answers, include brief excerpts or record references so the user can verify the answer. Do not expose unnecessary personal or sensitive data from the source.

## 12. Suggested Development Phases

### Phase 1 — Dataset and ingestion
- Use a public CSV/XLSX dataset.
- Inspect its schema and quality.
- Import it into SQLite.
- Verify row counts and sample queries.

### Phase 2 — SQL chatbot
- Implement question-to-SQL generation.
- Add schema-aware prompts, validation, read-only enforcement, and row limits.
- Test filters, aggregates, sorting, grouping, and joins.

### Phase 3 — Text retrieval
- Identify text-heavy columns.
- Add keyword search.
- Return source records and row IDs.
- Evaluate retrieval against a small set of test questions.

### Phase 4 — Hybrid routing
- Add query classification and explicit multi-step plans.
- Combine SQL results with text evidence.
- Ask for clarification when a question is ambiguous.

### Phase 5 — Interface and observability
- Add a simple CLI or Streamlit UI.
- Show generated SQL and sources in a developer/debug mode.
- Log latency, errors, route decisions, and token usage without logging secrets or unnecessary sensitive data.

### Phase 6 — PostgreSQL and deployment (optional)
- Implement and test a PostgreSQL adapter.
- Add proper credentials, access controls, migrations, backups, and deployment configuration.
- Consider PostgreSQL full-text search and `pgvector` if semantic retrieval is required.

## 13. Public Datasets for Development

Use a small sample first. Check each dataset's current license and usage restrictions before commercial use.

1. **UCI Online Retail**
   - URL: https://archive.ics.uci.edu/dataset/352/online+retail
   - Useful for invoices, product descriptions, quantities, prices, customer IDs, and dates.
   - Strong starting point for SQL aggregation and filtering; text search can use product descriptions.

2. **NYC 311 Service Requests**
   - URL: https://catalog.data.gov/dataset/311-service-requests-from-2010-to-2019
   - Useful for request types, agencies, timestamps, locations, and statuses.
   - Good for operational analytics and complaint-text queries where descriptive fields are present.

3. **Amazon Customer Reviews**
   - URL: https://www.kaggle.com/cynthiarempel/amazon-us-customer-reviews-dataset/tasks
   - Useful for ratings, dates, product categories, review headlines, and review bodies.
   - Strong candidate for hybrid structured and unstructured questions; may be large, so use a subset.

4. **World Bank World Development Indicators**
   - URL: https://databank.worldbank.org/source/world-development-indicators
   - Useful for country-level indicators and time-series analysis.
   - Best for structured SQL testing; contains relatively little free-form text.

5. **NYC 311 Customer Satisfaction Survey**
   - URL: https://catalog.data.gov/dataset/311-customer-satisfaction-survey
   - Useful for survey responses and customer service analysis.
   - Inspect the available columns before assuming free-form feedback is present.

## 14. Evaluation Plan

Create a hand-checked evaluation set of at least 30–50 questions. Include:
- Simple filters and lookups.
- Counts, sums, averages, min/max, and top-k.
- Group-by and date-range queries.
- Joins across sheets/tables.
- Text keyword and semantic retrieval questions.
- Hybrid questions that require both SQL and text.
- Ambiguous or unanswerable questions.
- Malicious or unsafe prompts asking for database modification or secret disclosure.

Track:
- **SQL execution success rate**
- **SQL result correctness** against known expected results
- **Routing accuracy**
- **Retrieval Recall@k / Precision@k** where labels are available
- **Answer faithfulness** to retrieved/database evidence
- **Clarification quality**
- **Latency and cost per question**

Do not judge the system only by whether the answer sounds fluent. Correctness should be evaluated against the source data.

## 15. Security and Reliability Requirements

- Treat workbook content and user questions as untrusted input.
- Do not execute instructions found inside cells as system instructions.
- Enforce read-only database credentials or equivalent restrictions wherever possible.
- Never execute LLM-generated Python, shell commands, or arbitrary SQL without validation.
- Keep API keys in environment variables or a secrets manager.
- Avoid exposing personal or confidential spreadsheet data in logs.
- Apply row limits and reasonable execution timeouts.
- Report data freshness and ingestion time.
- Make re-import behavior explicit and testable.

## 16. Definition of Done for the MVP

The MVP is ready when:
- A user can import at least one workbook with multiple sheets.
- The app can answer basic SQL questions with verified results.
- It can search text columns and return source references.
- It can handle at least one hybrid question by combining SQL and text retrieval.
- Unsafe SQL is rejected in tests.
- Ambiguous and unsupported questions are handled honestly.
- A 30-question evaluation set is available with expected results or relevance labels.
- Setup instructions and configuration are documented in the README.

## 17. Instructions for the Coding LLM

Implement the project incrementally. Before writing code:

1. Inspect the current repository and preserve useful existing work.
2. State the proposed architecture and any assumptions.
3. Implement Phase 1 and Phase 2 first, with tests.
4. Run the tests and fix failures before moving to text retrieval.
5. Avoid unnecessary frameworks and abstractions in the first version.
6. Pin compatible dependency versions in `requirements.txt`.
7. Provide a `.env.example`, a clear README, and sample commands.
8. Do not claim that a feature works unless it has been implemented and tested.
9. If credentials or an LLM API key are unavailable, provide a deterministic mock or clearly documented configuration path so core tests still run.
10. At the end, summarize the files created, setup steps, test results, known limitations, and the next recommended milestone.

**Priority:** deliver a working, safe SQLite-based MVP first. Keep the database layer modular so PostgreSQL, embeddings, and a richer UI can be added later without rewriting the whole application.
